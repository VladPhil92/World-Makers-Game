# N2 — Authored Activation & Release Candidate

## Purpose

N1 can prove that the complete authored stack exists and can emit an `ACTIVATION_CANDIDATE`. N2 is the deliberately separate phase that turns an approved candidate into an authored runtime takeover and, only after that takeover is proven on the exact committed build, into a visual `RELEASE_CANDIDATE` for P5/V8 certification.

N2 does not auto-commit visual activation and it does not delete procedural fallback assets.

## State model

N2 has exactly three states:

- `BLOCKED` — activation provenance, native inventory, registry parity or runtime takeover is incomplete.
- `ACTIVATION_READY` — a human-approved N1 candidate has passed hash/provenance checks and may be committed deliberately.
- `RELEASE_CANDIDATE` — the committed activation is present in both canonical and packaged P1 registries, native inventory belongs to that exact commit and runtime takeover has been proven.

`ACTIVATION_READY` is not a release candidate.

## Rehearsal vs committed activation

### Rehearsal

A rehearsal downloads an N1 artifact, verifies the exact candidate SHA-256 and applies the candidate only inside the workflow workspace. The canonical and packaged P1 registry copies are temporarily made authored-active so the native import/runtime path can be exercised.

A rehearsal is useful for catching integration failures, but it **cannot** become `RELEASE_CANDIDATE` because the checkout no longer represents the committed tree identified by `github.sha`.

### Committed

Committed mode requires a human-reviewed repository change containing:

1. the exact N1 candidate applied to `content/visual/authored/authored-assets-p1.json`;
2. the identical packaged registry at `game/Content/WorldMakers/Visual/Authored/authored-assets-p1.json`;
3. `content/visual/authored/n2-activation-provenance.json` generated by `apply-n2-authored-activation.py --mode committed`.

The activation tool never performs `git commit`, `git push` or a GitHub write. Human review is mandatory.

## Candidate integrity

The activation tool accepts only an N1 result whose status is `ACTIVATION_CANDIDATE`. The candidate hash must equal the explicitly approved SHA-256. It must differ from the fail-closed P1 registry only by changing every `authoredPresent` field from `false` to `true`.

IDs, object paths, source paths, LOD requirements, material-slot limits, collision policy and fallback policy cannot drift during activation.

Partial activation is forbidden.

## Runtime takeover

N2 extends the source runtime so the authored stack can actually win when an activated registry is present.

### Environment

The P1 bridge retains the existing nine-family all-or-nothing rainforest takeover. Authored HISM render families become visible only when all required meshes load and pass their P1 contracts. Procedural environment geometry is hidden only after successful authored activation; proxy collision remains authoritative.

### Character and animation

`SK_WM_ChildExplorer` alone is insufficient. The bridge also requires `ABP_WM_ChildExplorer` to load as an animation-blueprint generated class. Only then may N2 override the V4 development preference for procedural avatar art in the current process and show the authored Skeletal Mesh.

The gameplay capsule and `CharacterMovementComponent` remain authoritative. Root motion is not introduced by N2.

### VFX

The 17 V6 semantic events now prefer their authored Niagara targets when `vfx.science.master` is deliberately activated in P1. If an individual Niagara system cannot load, V6 falls back to the existing procedural effect instead of losing causal feedback.

The VFX layer remains presentation-only and has no reward, evidence, purchase or mission authority.

### Presentation

The release takeover requires the native presentation assets already inventoried by P5. N2 does not reinterpret gameplay state through cinematics; V7 control-preservation and reduced-motion rules remain authoritative.

## Runtime takeover report

`UWMAuthoredVisualBridgeSubsystem` supports a native evidence mode through:

- `-WMN2TakeoverReport=<path>`
- `-WMBuildCommit=<40-character SHA>`

During game runtime it retries authored visual preparation, then emits a fail-closed report containing:

- authored environment active;
- procedural environment hidden;
- authored avatar active;
- procedural avatar inactive;
- authored Animation Blueprint active;
- authored VFX ready;
- authored presentation ready.

A report with any failed takeover condition is `BLOCKED`.

## Release fingerprint

`assess-n2-release-candidate.py` hashes the canonical registry, packaged registry, activation provenance, P5 native inventory and runtime takeover report. The P5 inventory and takeover report must both identify the exact release commit.

A `RELEASE_CANDIDATE` is therefore tied to one committed source tree and one native Content state.

## Procedural fallback and rollback

Procedural fallback is intentionally retained through N2. Rolling back the activation commit restores `authoredPresent=false`, after which P1/V3/V4/V6 paths remain available without deleting authored binary assets.

This makes rollback a registry/provenance change rather than destructive art deletion.

## P5 and V8 handoff

`RELEASE_CANDIDATE` is still **not device certification**. The exact activated commit must then pass:

- P5 art-polish/native inventory requirements;
- V8 performance evidence;
- Android Low/Mid/High;
- iPadOS Low/Mid/High;
- exact-build hashes and human visual review.

N2 proves authored activation and runtime takeover. P5/V8 prove production quality and device fitness.

## Source-complete boundary

The N2 source phase is complete when the activation/release assessors, runtime authored preference, Niagara fallback path, runtime takeover report, manual native workflow, documentation and Repository Quality gate pass.

Without a real N1 candidate, committed `.uasset` stack and self-hosted Unreal 5.8.2 execution, N2 must remain `BLOCKED`; source CI must not fabricate a release candidate.
